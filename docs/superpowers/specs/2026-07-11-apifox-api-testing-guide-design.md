# Apifox 双角色接口测试手册设计

## 目标

在不修改后端业务代码的前提下，生成一份可直接照着操作的中文 Apifox 测试手册。手册覆盖业务管理员与普通用户两种角色，从账号注册、登录、JWT Token 管理开始，完成分类、商品、购物车、订单及订单详情的正向和负向测试。

最终交付文件为 `docs/apifox_api_testing_guide.md`。

## 事实来源

手册以当前仓库代码为准，主要依据：

- `config/urls.py` 与各应用的 `urls.py`：确定真实 URL 和允许的 HTTP 方法。
- 各应用的 `serializers.py`：确定请求字段、必填规则和校验条件。
- 各应用的 `views.py` 与 `services.py`：确定权限、业务动作、状态变化和响应状态码。
- 各应用的 `tests.py`：确认核心成功路径和错误码。
- `config/settings.py`、`README.md` 与 `docker-compose.yml`：确定 JWT、分页和运行地址。

## 范围边界

### 包含

- Docker 与本地运行两种基础地址。
- Apifox 项目、环境、公共变量和 Bearer Token 配置。
- 管理员与普通用户均从注册接口开始创建。
- 注册后的管理员候选账号通过 Django Shell 提升为 `role=admin`，因为注册接口不接收 `role`。
- 认证：注册、登录、当前用户、刷新 Token。
- 分类：管理员列表、详情、创建、完整更新、部分更新、软删除；公开列表验证。
- 商品：管理员列表、详情、创建、完整更新、部分更新、软删除；公开列表、详情与筛选验证。
- 购物车：查看、首次添加、重复添加累加、部分更新、删除、清空。
- 订单：创建、列表、状态筛选、详情、支付和取消。
- 管理员查看所有订单与任意订单详情，普通用户只能查看自己的订单。
- 无 Token、错误 Token、普通用户调用管理接口、库存不足、商品下架、非法订单状态等负向场景。
- 对订单发送 `PUT`、`PATCH`、`DELETE`，验证当前项目返回 `405 Method Not Allowed`。

### 不包含

- 不为订单增加当前代码中不存在的通用更新或删除接口。
- 不修改项目权限、序列化器、服务或数据库模型。
- 不包含真实支付、前端页面、性能压测或并发压测。
- 不要求导出 Apifox JSON 项目文件，只交付 Markdown 操作手册。

## 文档组织方案

采用“端到端双角色场景”为主线，并在结尾提供接口速查表和角色权限矩阵。这样既能按顺序完成一轮测试，又便于后续单独复测某个接口。

每个请求统一包含：

1. 测试目的与前置条件。
2. Apifox 中的目录位置和请求名称。
3. HTTP 方法与 `{{base_url}}` URL。
4. 是否携带管理员或普通用户 Bearer Token。
5. Query 参数或 JSON 请求体。
6. 发送后的变量提取方式。
7. 预期 HTTP 状态码、业务 `code` 和关键响应字段。
8. 失败时的排查建议。

## Apifox 环境设计

推荐 Docker 全栈测试，设置：

```text
base_url = http://127.0.0.1:8080
```

本地 `runserver` 备选设置：

```text
base_url = http://127.0.0.1:8000
```

环境变量至少包括：

```text
run_id
admin_username
admin_password
admin_access
admin_refresh
user_username
user_password
user_access
user_refresh
category_id
product_id
cart_item_id
pending_order_id
paid_order_id
cancelled_order_id
```

`run_id` 用于拼接用户名和唯一 `slug`，避免重复执行时触发唯一约束。手册会给出可直接填写的示例值，并说明每轮测试前更换该值。

## 端到端数据流

1. 启动服务并调用 `/api/health/`。
2. 注册管理员候选账号和普通用户账号。
3. 用 Django Shell 将管理员候选账号的 `role` 更新为 `admin`。
4. 分别登录并保存两个角色的 access、refresh Token。
5. 调用 `/api/auth/me/` 确认两个角色。
6. 管理员创建并修改分类，再创建和修改商品。
7. 普通用户读取公开商品，并验证不能调用管理商品接口。
8. 普通用户添加、累加、修改和删除购物车项。
9. 重新添加商品并创建第一笔订单，保存为 `paid_order_id`，随后支付。
10. 再次添加商品并创建第二笔订单，保存为 `cancelled_order_id`，随后取消并检查库存恢复。
11. 再创建一笔保持 `pending` 的订单，用于状态筛选和订单详情测试。
12. 管理员查询全部订单和普通用户的订单详情。
13. 普通用户尝试访问不属于自己的订单，并验证资源不可见。
14. 对订单尝试 `PUT/PATCH/DELETE`，记录 `405`。
15. 最后下架商品和停用分类，验证普通用户不可见且不能加入购物车。

## 权限设计

- 注册、登录、刷新 Token：匿名可访问。
- 当前用户、购物车、订单：必须携带有效 access Token。
- 公开分类和商品：匿名可读。
- 管理分类和商品：仅 `role=admin` 或超级用户可访问。
- 普通用户订单：查询集限定为当前用户。
- 管理员订单：可以查询所有用户订单和详情。
- 管理员同样是已认证用户，因此可以使用购物车和订单接口；主测试链路仍以普通用户作为买家。

## 响应和错误验证

成功响应统一检查：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

分页接口检查 `data.count`、`data.next`、`data.previous` 和 `data.results`。错误测试同时检查 HTTP 状态码与业务 `code`，重点覆盖：

- `40001`：库存不足。
- `40002`：商品已下架。
- `40003`：购物车为空。
- `40004`：订单状态不允许操作。
- `40100`：未认证或认证失败。
- `40300`：无权限。
- `40400`：资源不存在或不属于当前用户。
- `40900`：订单重复提交锁冲突。

当前异常处理器没有为 HTTP `405` 单独分配业务码，因此手册会把 HTTP `405` 作为主要断言，并按实测结果记录响应体业务码，不把它描述成订单业务错误。

## 测试数据与清理策略

- 商品库存设置为足以完成支付、取消和待支付三条订单链路的值。
- 每次创建订单前重新向购物车添加商品，因为成功创建订单会删除已选中的购物车项。
- 商品和分类删除是软删除：商品状态改为 `inactive`，分类 `is_active` 改为 `false`。
- 用户、订单和订单明细没有清理 API。重复执行时通过更换 `run_id` 避免用户名和 `slug` 冲突。
- 测试结尾提供可选的开发数据库重置说明，但不把破坏性清理作为常规步骤。

## 验证策略

生成手册后执行以下检查：

1. 使用 Django URL resolver 验证文档中的每个路径都能解析。
2. 通过序列化器字段检查请求体字段和必填项。
3. 运行 `python manage.py check`。
4. 运行 `python manage.py test`，确认现有接口行为未被文档工作改变。
5. 检查 Markdown 中不存在未完成标记、错误占位符或未解释变量。
6. 对照权限类、视图和服务逐项核对预期状态码与业务状态变化。

## 完成标准

- 新用户能仅依赖该手册在 Apifox 中配置环境并完成整条测试链路。
- 每个步骤都明确说明使用哪个角色和哪个 Token。
- 所有 URL、方法、字段、状态码和权限规则与当前仓库一致。
- 商品、购物车的增删改查得到完整覆盖。
- 订单按当前业务接口覆盖创建、查询、详情、支付、取消，并明确通用更新与删除不受支持。
- 文档包含可复用的变量提取、断言思路、执行顺序、权限矩阵和错误排查。
