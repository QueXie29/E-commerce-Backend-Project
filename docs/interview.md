# 面试讲解

## 1 分钟版本

我做的是一个轻量级电商后端系统，主要模拟真实电商里的用户、商品、购物车和订单交易流程。技术上使用 Django REST Framework 开发 API，使用 SimpleJWT 做登录认证，使用 MySQL 存储业务数据，Redis 用于商品缓存、重复提交锁和 Celery Broker。创建订单时通过数据库事务和 `select_for_update` 行级锁维护库存一致性；待支付订单提交后发送 Celery 超时消息，到期任务锁定订单并重检状态，只取消仍未支付的订单并恢复库存，同时用 Celery Beat 扫描补偿漏消息。最后使用 Docker Compose 编排整个服务链路。

## 3 分钟版本

这个项目是一个轻量级电商后端系统，业务链路包括用户注册登录、商品浏览、加入购物车、创建订单、库存扣减、模拟支付和取消订单。

技术选型上，我使用 Django REST Framework 作为 API 框架，SimpleJWT 实现 JWT 登录认证，MySQL 存储用户、商品、购物车、订单和订单明细数据，Redis 负责商品缓存、订单重复提交锁和 Celery 消息代理，Celery Worker 消费订单超时任务，Celery Beat 执行补偿扫描，最后用 Docker Compose 编排这些服务。

项目中我重点关注两个后端常见问题。第一个是库存一致性。创建订单时，我没有简单地先查库存再扣库存，而是在 `transaction.atomic()` 事务中使用 `select_for_update()` 锁定商品行，检查库存充足后再扣减库存、增加销量、创建订单、创建订单明细并删除购物车项。这样可以保证这些操作要么全部成功，要么全部回滚，避免并发下单导致库存被扣成负数。

第二个是接口幂等和重复提交。用户可能连续点击提交订单，所以我在创建订单前加了 Redis 锁，key 根据 `user_id` 生成，并设置 10 秒过期时间。如果锁已经存在，就返回重复提交提示。订单处理结束后，在 `finally` 中检查锁 value 并释放锁，避免误删其他请求的锁。

此外，商品详情接口使用 Redis 缓存，采用 Cache Aside 模式：先查缓存，未命中再查数据库并回写缓存；商品更新、下架、扣库存或恢复库存时删除相关缓存，减少旧数据问题。

第三个问题是待支付订单长期占用库存。创建订单时把固定的 `expires_at` 写入 MySQL，事务提交后发送 ETA 消息。消费者到期后在事务内锁定订单行并重检 `pending` 和截止时间，再按商品 ID 顺序锁定商品行、恢复库存并把状态改为 `cancelled`。支付、人工取消和重复消息都竞争同一把订单行锁，所以只有第一个合法状态迁移生效；如果发布消息时 Redis 不可用，Celery Beat 会按 `(status, expires_at)` 索引扫描并重新入队。

## 常见问题

### Django 和 DRF 的关系是什么？

Django 是 Web 框架，提供 ORM、路由、中间件、认证、后台管理等能力。DRF 是构建 Web API 的扩展框架，提供 Serializer、APIView、ViewSet、权限、认证、分页等能力。

### Serializer 的作用是什么？

Serializer 负责输入校验、数据反序列化和输出序列化。比如注册接口中校验密码长度和两次密码是否一致，商品接口中把 ORM 对象转换成 JSON 响应。

### ViewSet 和 APIView 有什么区别？

APIView 更灵活，适合注册、登录、购物车聚合这类自定义流程。ViewSet 更适合资源型接口，比如商品和订单的列表、详情、创建等操作，可以结合 Router 或 action 简化路由。

### JWT 和 Session 有什么区别？

Session 通常在服务端保存登录状态，客户端保存 session id。JWT 把用户身份信息签名后放在 token 中，客户端通过 `Authorization: Bearer <token>` 访问接口，更适合前后端分离和移动端场景。

### 为什么订单和订单明细要拆成两张表？

订单主表记录订单级信息，比如订单号、用户、总金额、状态。订单明细记录每个商品的价格、数量和小计。拆分后可以支持一个订单包含多个商品，也方便查询和扩展。

### 商品价格为什么要在订单明细中保存快照？

商品后续可能改名或改价，但历史订单金额不能变。订单明细保存下单时的商品名称和价格，可以保证历史交易数据稳定。

### 什么是数据库事务？

事务保证一组数据库操作要么全部成功，要么全部失败。创建订单时，扣库存、创建订单、创建明细、删除购物车必须在同一个事务中，否则可能出现库存扣了但订单没创建的问题。

### `select_for_update()` 的作用是什么？

`select_for_update()` 会在事务中对查询到的行加排他锁。并发创建订单时，多个请求不能同时修改同一商品库存，后来的请求会等待前面的事务完成，从而避免超卖。

### 如何避免库存超卖？

本项目使用数据库事务和行级锁。下单时在事务中锁定商品行，检查库存是否足够，再扣减库存。如果库存不足就抛出异常并回滚事务。

### 为什么商品详情适合做缓存？

商品详情读多写少，访问频率高，数据结构相对稳定。放入 Redis 可以减少数据库查询压力，提高响应速度。

### 什么是 Cache Aside Pattern？

Cache Aside 是旁路缓存模式：读数据时先查缓存，缓存未命中再查数据库并写入缓存；写数据时先更新数据库，再删除缓存。

### 商品更新后如何保证缓存一致性？

商品创建、修改、下架、扣库存或恢复库存后删除 `product:detail:{id}` 缓存。下次读取商品详情时重新从数据库加载并回写缓存。

### Redis 锁如何防止重复提交？

创建订单前使用 `cache.add(lock_key, lock_value, timeout=10)`。如果 key 已存在，说明该用户已有订单请求在处理中，直接返回重复提交。处理完成后检查 value 再删除锁。

### Redis 锁有什么问题？如何优化？

简单 Redis 锁可能遇到业务执行时间超过锁过期时间、锁误删、Redis 故障等问题。可以通过唯一 value、释放前校验 value、合理 TTL、Lua 脚本原子释放、续期机制等方式优化。

### 为什么购物车数据放 MySQL，而不是全部放 Redis？

购物车是用户长期业务数据，需要持久化、跨设备可见，并且要和商品、订单关联。Redis 更适合缓存和短期锁，不适合作为唯一数据源保存购物车。

### 创建订单为什么要使用事务？

创建订单涉及多张表和库存变更。如果不使用事务，可能出现订单创建成功但库存没扣、库存扣了但订单明细没生成等不一致问题。

### 如果用户取消订单，库存如何恢复？

取消待支付订单时，在事务中锁定订单和商品行，把订单明细中的商品数量加回库存，并将销量回退，然后把订单状态改为 `cancelled`。

### 如果支付成功后还能取消，会有什么问题？

已支付订单如果随意取消，会导致资金状态、库存状态和订单状态不一致。真实业务中已支付订单应走退款流程，而不是普通取消流程。

### 为什么超时取消要用消息队列，还要保留定时扫描？

每单 ETA 消息可以在截止时间附近主动处理，不需要高频扫描全部订单；但“数据库已提交、消息尚未成功发布”不是一个原子事务，Broker 或 Worker 停机也可能让消息延迟。因此订单截止时间仍落在 MySQL，Celery Beat 每分钟只扫描到期的 `pending` 订单并重新入队作为补偿。消费者必须幂等，不能假设消息只投递一次。

### 超时任务和支付同时发生，如何避免把已支付订单取消？

两个流程都会在 `transaction.atomic()` 中用 `select_for_update()` 锁定同一条订单记录。先拿到锁的一方完成状态迁移，后拿到锁的一方重新读取状态：如果支付先完成，超时任务看到 `paid` 后直接结束；如果截止时间已到且超时取消先完成，支付看到 `cancelled` 后拒绝。订单行锁保护的是状态迁移，商品行锁保护的是库存恢复。

### 项目如何扩展优惠券、支付和物流？

优惠券可以新增优惠券表和订单优惠明细；支付可以新增支付流水表和回调验签逻辑；物流可以新增发货单和物流轨迹表。扩展时仍要保持订单状态流转清晰。
